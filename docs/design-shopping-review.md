# 电商视频理解与个性化推荐 — 设计稿

> 用途:①把"购物向视频的针对性内容分析"落成可施工的设计;②作为面试/简历里关于
> **视频理解 · Prompt 优化 · Agent 工作流**三块的一页说明。
> 状态:**设计,未实现**。文中标注了哪些零件是**已实现且真机验证过**的(可讲),
> 哪些只是设计(别讲成做了)。
> 触发来源:恒洁集团 AI 产品岗 JD 第 4 条「视频理解与内容分析:结合语音、文字和画面
> 信息,落地商品卖点提取、内容标签、关键片段定位」。

---

## 0. 一句话方案

把现有 MemVault 的**三个已有零件**(提示词版本化、UP 规则路由、个人画像)接起来,
再给视频管线补一层**购物复盘 schema**(卖点 / 标签 / 关键片段,且每条结论带时间戳证据),
最后把用户偏好作为一维排序信号注入检索。

## 1. 现状:可直接复用的地基(已实现)

| 能力 | 位置 | 关键事实 |
|---|---|---|
| 多模态采集 | `pipeline/video.py` | 抽帧 **全片覆盖**(40 帧,0~时长)+ ASR 分段带 `start/end` + 画面 OCR(人声占比 <30% 才跑)+ `content_text = 语音 + 画面文字` |

| 提示词版本化 | `prompts.py`(`prompts` 表) | `(name, stage, category_id, version, status, origin)`;`new_version` 自动退役旧版、支持 `rollback` |
| 质疑驱动进化(Flow C) | `prompts.rewrite_from_feedback` | 用户质疑 → 向量召回同分类历史质疑 → LLM 改写新版 → 回归集对比 → 应用;真机跑通过 |

| 个人画像 | `profile(domain, key, value_json, source)` | 聊天里说"我身高178"→ chat 抽取链路自动落库 |

| 面板/接口 | `server/api.py`(统一契约)+ `web/`(Vue) | 待整理箱、检索页已迁 Vue;JSON 契约 `{ok,data,error}` |

> **②带证据的结构化输出**(现在 `attrs_ai` 是"若干属性",没有片段/证据概念)。

## 2. L1:提示词从"按分类"扩到"按规则命中"

### 2.1 问题

当前提示词绑定维度只有一个:`category_id`。而"某个 UP 的带货视频要走购物复盘提示词"
不是分类问题——同一个 UP 可能横跨多个分类,同一分类也混着测评号和带货号。

### 2.2 设计:规则表 + 确定性解析

```sql
CREATE TABLE prompt_bindings (
  id          INTEGER PRIMARY KEY,
  kind        TEXT NOT NULL,      -- up | up_set | domain | source_type | keyword
  target      TEXT NOT NULL,      -- up_mid / "123,456" / 'shopping' / 'video' / 关键词或正则
  stage       TEXT NOT NULL,      -- extract | router | clip
  prompt_name TEXT NOT NULL,      -- 指向 prompts.name,如 'shopping_review'
  priority    INTEGER DEFAULT 0,  -- 大者先命中
  enabled     INTEGER DEFAULT 1,
  note        TEXT,               -- 绑定原因(人工可读)
  created_at  TEXT DEFAULT (datetime('now','localtime'))
);
```

解析顺序(在 `extract_item` / `route_item` 前置一步,与现有 UP 规则同一层):

```
1) prompt_bindings 命中(UP/UP集 → profile)   ← 新增:确定性,不花 LLM 判断
2) 分类绑定提示词(prompts.category_id)         ← 现状不变
3) 通用提示词                                   ← 兜底
```

### 2.3 三个护栏(沿用项目已有做法)

- **命中可审计**:命中后写进 `items.auto_note`("命中规则「×UP集」→ profile=shopping_review"),
  条目页可见;规则表带 `note` 字段说明为什么绑。
- **提示词照样版本化**:新 profile 只是 `prompts.name` 的新值;改动走 `new_version`,
  可 diff、可 `rollback`(已实现)。
- **不做隐式猜测**:UP→profile 的绑定必须人工确认(与 UI 上「📌 该 UP 的视频都归此分类」
  同一交互位),避免"模型自己决定用哪套提示词"导致不可复现。

## 3. L2:购物复盘提取 profile(JD 第 4 条的正题)

### 3.1 输出 schema(能力边界写死在 schema 里)

```jsonc
{
  "商品": [{"名称": "", "品类": "", "品牌": "", "价格": "", "优惠": ""}],
  "卖点": [{"点": "面料抗风", "证据": "台词『这个面料…』", "ts": 132.4,
            "来源": "asr"}],                    // asr | ocr | frame
  "目标人群": {"人群": "", "场景": ""},
  "内容结构": [{"段": "口播介绍",  "start": 0,   "end": 48},
               {"段": "上身演示",  "start": 48,  "end": 210}],
  "关键片段": [{"start": 210, "end": 246,
                "kind": "价格播报",             // 价格播报|卖点演示|对比|上身效果|尺码建议
                "reason": "", "confidence": 0.8}],
  "内容标签": ["男装", "休闲风", "通勤", "春秋", "棉质"],
  "模态说明": "该视频无口播,内容来自画面字幕"     // 缺模态时显式声明,不硬编
}
```

要点:

- **每条卖点/片段必须带 `ts` 证据**——这是"有据可查"在提取层的对应物,
  也是防幻觉的第一道闸;前端点一下即可跳 B 站 `?t=`(跳转链接已实现)。
- **`内容标签` 是给 L3 用的燃料**:风格/场景/季节/材质四类,取值收敛在词表内(见 §4.2)。
- **`模态说明`** 让"字幕无配音视频"这类情况可解释(本项目真实案例:#14 冰淇淋视频
  6 分 31 秒里只有 36 秒人声,纯靠画面字幕才没被误判成广告)。

### 3.2 输入:多模态时间轴(不是纯正文)

当前 `classify._extraction_text` 喂的是 `content_text`(ASR + 画面文字拼接,3000 字预算)。
购物复盘要做**片段切分**,必须保留时间对齐:

```
[00:00] 语音:朋友们今天这件冲锋衣…
[00:48] 画面文字:三层复合面料 / 防水 10000mm
[01:12] 关键帧:上身演示(CLIP 命中"外套 上身")
[02:10] 语音:价格这块,平时八百多,今天…
```

组装成本与今天相同(仍受 3000 字预算约束),但模型获得了"什么时候发生了什么"。

**长视频必须分段再合并(map-reduce)**:本项目的实测教训是长视频只喂开头会漏后段
(16468 字的视频曾只覆盖 18%),片段定位对这条尤其敏感。

### 3.3 证据校验(复用 DESIGN §13.1 的既有护栏)

输出后做一次后校验:

1. `ts` 必须落在该条目真实 chunk 的时间戳集合内(容差 ±2s);
2. `来源` 不能引用该视频不存在的模态(没有口播就不能给 `asr`);
3. 不合格的字段**丢弃并记日志**,不静默保留。

### 3.4 落库与可视化

```sql
CREATE TABLE clips (
  id INTEGER PRIMARY KEY,
  item_id   INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  start_ts  REAL NOT NULL,
  end_ts    REAL,
  kind      TEXT NOT NULL,          -- 价格播报/卖点演示/对比/上身效果/尺码建议
  reason    TEXT,
  confidence REAL,
  created_at TEXT DEFAULT (datetime('now','localtime'))
);
```

面板:条目详情页在"语义块时间轴"上加一段**高亮片段条**(kind 配色),点击跳 `?t=`。
效果形态 = JD 里"为内容优化及商品运营提供支持"的可演示界面。

## 4. L3:个性化(男装:休闲 / 商务倾向)

### 4.1 信号来源(按可得性排序)

| 层 | 信号 | 现状 |
|---|---|---|
| 显式 | 聊天说"我爱穿商务风" → `profile(domain='shopping', key='风格倾向', value={'休闲':0.6,'商务':0.4}, source='chat')` | **链路已在**(chat 抽取 → `upsert_profile`) |
| 弱显式 | 加购、手动归类、归档动作 | `jd_cart` 任务与分类操作有记录,聚合即可 |
| 隐式 | 检索词、反复查看、停留时长 | **目前没有检索历史表**——唯一需要新增埋点的地方 |

### 4.2 存哪:偏好权重表(而非只靠 profile)

`profile` 适合放"人给的事实";机器累计的权重建议单独放,便于审计与回溯:

```sql
CREATE TABLE preferences (
  id INTEGER PRIMARY KEY,
  domain   TEXT NOT NULL,
  kind     TEXT NOT NULL,        -- 风格 | 品类 | 季节 | 材质
  value    TEXT NOT NULL,        -- 休闲 / 商务 / 冲锋衣 / 春秋 / 棉
  weight   REAL NOT NULL,        -- 0~1
  source   TEXT,                 -- chat | behavior | manual
  evidence TEXT,                 -- 触发它的条目 id 列表(可解释)
  updated_at TEXT DEFAULT (datetime('now','localtime')),
  UNIQUE(domain, kind, value)
);
```

**更新走周期 job**(每日/每周聚合),不在请求路径里实时改画像——否则一次误点永久污染。

### 4.3 三个消费落点(价值递增)

1. **提取阶段(轻)**:把偏好作为提示词变量注入(`{style_preferences}`),
   让模型多输出一列"与偏好匹配度";**提取内容保持客观**,匹配度单独成列。
2. **检索重排(主)**:`memory.search()` 现在只有 RRF 融合分,加一维
   `personal = Σ(标签权重 × 商品标签命中)`;最终 `score = RRF + α·personal`。
   这是"把偏好变成排序"的地方,也是最好演示的地方。
3. **技能上下文**:`SkillSpec`(购物技能)已经注入 profile,偏好天然可用。

### 4.4 护栏

- 每条权重带 `source` 与 `evidence`(能回答"为什么排这个在前面");
- 面板可查看/编辑/清空偏好(画像本来就该可见);
- **保留探索比例**(如 10% 结果不加权),否则越推越窄;
- 偏好与检索解耦:偏好只影响排序,不参与过滤 → 想清空时一条 SQL 即可回到基线。

## 5. ReAct 的边界(别滥用的理由)

| 场景 | 该用什么 | 理由 |
|---|---|---|
| 卖点提取 / 打标 / 片段定位 / 偏好排序 | **固定管线 + 规则 + schema 校验** | 路径可预知;可复现、可回归、便宜;失败可定位到某一步 |
| "复盘这条直播卖点,并与库里同品类商品对比" | **有界 ReAct** | 需要多轮检索 + 动态决定下一步查什么 |
| 新 UP 冷启动(判断是带货号还是测评号) | Agent 探测 + **人工确认绑定** | 结论要落到规则表,不能每次现算 |

有界 ReAct 的约束沿用 DESIGN §13.3:工具白名单、最大步数、批量入库前人工确认。

## 6. 实现顺序(每步都可独立验证)

| 步 | 内容 | 验证方式 |
|---|---|---|
| ① | 一个 profile + 一条规则:`prompts.name='shopping_review'` + `prompt_bindings` 表 + 解析前置一步 | 用库里任一条购物向视频跑通,卖点/片段都带时间戳 |
| ② | `clips` 落库 + 条目页片段条(可点跳转) | 面板可见 + 跳 B 站对应秒 |
| ③ | 多模态时间轴输入 + 证据校验(丢幻觉字段) | 构造一段"无口播只有字幕"的视频验证模态声明 |
| ④ | 检索重排接入偏好(先只用显式偏好,不碰埋点) | 同一查询在有/无偏好下排序变化可解释 |
| ⑤ | 埋点(检索历史)+ 周期聚合 job | 跑一周后偏好权重应稳定、可解释 |
| ⑥ | 有界 ReAct(仅调研型任务) | 步数与工具调用可审计 |

## 7. 成本与风险

| 项 | 评估 |
|---|---|
| LLM 成本 | 每个视频多 1 次提取调用(长视频分段则 ×N);建议只对命中规则的视频启用(即 L1 的价值:按需付费) |
| 提取质量 | 片段定位依赖时间戳粒度:ASR 段 5~45s 较准;画面帧 40 帧/整片 → 粗(约 每 10s 一帧),必要时对判定为"购物向"的视频加密抽帧 |
| 偏好污染 | 周期聚合 + 探索比例 + 可清空(见 §4.4) |
| 数据合规 | 只处理用户自己采集的公开内容;`config/cookies.txt`、`.env` 永不入库/输出(项目已约定) |
| 复杂度 | L1/L2 是"接线 + schema",L3 才引入新表与 job;不要一次全上 |

UP 规则路由是**已实现且真机验证**(129 个 pytest + 浏览器实测);卖点/片段 schema、
规则绑定表、偏好重排是**本设计稿**,尚未实现。

### 一句话电梯稿

> "我把自用的多模态记忆库当练兵场:视频进来先做语音+画面双路理解,画面文字在'人声很少'
> 时才自动跑 OCR——因为这能救回'字幕教学视频被当成广告'那类误判。内容分析不是一次性总结,
> 而是按规则匹配的**带证据结构**:每条卖点都指向某个时间戳。规则命中谁用哪套提示词是
> 确定性的、可审计的,提示词本身带版本与回滚。个性化只在排序层起作用,可一键清空——
> 我不想把确认偏差固化进系统。"

## 9. 验收标准(若实施)

- [ ] 命中规则的视频,`attrs_ai` 里 `卖点/关键片段` 全部带 `ts`,且 `ts` 在校验集合内;
- [ ] 未命中的视频走原提取路径,行为与今天**完全一致**(零回归,`pytest` 全绿);
- [ ] `clips` 在条目页可见、可点击跳转到视频对应秒;
- [ ] 无口播视频的 `模态说明` 正确声明来源(而不是编造口播内容);
- [ ] 偏好影响排序但不影响召回集合;清空偏好后排序回到基线。
