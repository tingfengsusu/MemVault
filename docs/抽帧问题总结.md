# 视频抽帧 / 语义块:当前问题清单(待设计)

> 用途:把"字幕类视频"的抽帧与语义块问题交给另一个会话做设计应对。
> 所有数字为本机实测(条目 #14《12 个脑洞大开的冰淇淋指南》,6 分 31 秒,字幕教学视频)。
> 相关代码:`memvault/vision/frames.py`、`memvault/pipeline/video.py`、`memvault/vision/ocr.py`。

## 一、现在的抽取与入库流程(实测)

```
下载 → 抽帧(≤40 帧)→ 每帧存图像块 → ASR → 按需 OCR(人声占比<30% 才跑)→ 汇总正文
```

- **抽帧** `frames.extract_frames`:全片均匀取 ≤600 个探测点(每点算相邻 HSV 直方图相关性)
  → 时间轴分 `max_frames`(=40)个桶 → **每桶取"画面变化最大"的点**;桶内无变化(相关性
  都 ≥0.45)则取桶首 → 回到这些时间点写 jpg。兜底:探测失败/帧太少时按固定间隔均分。
- **OCR** 对**每一张被抽到的帧**跑 EasyOCR(`canvas_size=960, mag_ratio=1.0`,实测
  1.17s/帧),识别出的**所有文字行合成一块** `[画面文字 mm:ss]`。
- **ASR** faster-whisper + VAD,碎句按 ~40 秒合并成段 `[语音 mm:ss]`。
- **入库**:图像块 `seq=0..n`,语音块 `seq=100+`,画面文字块 `seq=200+`;文本块进
  Chroma(bge-small-zh)+ FTS5,图像块进 `chunk_image`(Chinese-CLIP)。
- **正文** `content_text` = 语音文本 + 画面文字文本(供 AI 提取/卡片摘要/双链用,
  **图像不参与**)。
- **展示**:条目详情页按 `seq` 排序 → 40 张帧 → 2 条语音 → 40 条画面文字(不是时间轴流)。

## 二、问题(按严重度)

### P1 字幕类视频的抽帧密度与字幕节奏脱节

| 指标 | 实测值 |
|---|---|
| 视频时长 / 抽帧数 | 391s / 40 帧 |
| 帧间隔 | 平均 **9.6s**,中位 10.1s,最大 **19s** |
| 该类视频字幕换行节奏 | **2~4s** |

推论:字幕行覆盖率约 **1/4**;每条字幕平均只被 0~1 帧采到,所以"配方步骤"级信息
(哪句话配哪段动作)基本采不全。

**根因**:场景检测(HSV 直方图相关性)对**静态画面 + 字幕变化**的视频几乎无效——
字幕变化不改变直方图,"取变化最大的点"退化成"取桶首",实际等价于**按 max_frames
把全片均分**,于是密度完全由 `frames.max_frames` 决定,与内容无关。

### P2 图文不配对(配方的最小单元被拆开)

配方步骤 = **一段动作画面 + 当句字幕**(例:"草莓加蓝莓、旺旺牛奶代替奶油" + 搅拌机画面)。
现在两者是**互不相干的两类块**:图像块只有 `media_path`,画面文字块只有文本,
同一时刻的两者中间隔着几十条记录(`seq` 分段排列)。没有任何字段或逻辑把它们绑定。

### P3 OCR 文本混入固定水印/台标,且未去重

- 每块平均 33 字,其中约 1/3 是水印:`胡仔一人食`(11/40 帧)、`胡仔`(8/40)、`人食`、
  `bilbli`…**几乎 40/40 帧都带**;另有跨帧重复的字幕行(同一句被多帧采到时)。
- 影响:嵌入与 FTS 索引被噪声稀释、AI 提取输入一半注意力在对抗水印、重采样后还会产生
  近似重复块(密度一提高就更明显)。

### P4 ASR 对这类视频几乎无贡献

2 段共 204 字,其中 184 字是插入的广告口播(VAD 已滤掉 5:54 非人声);
真正的内容 100% 来自画面文字。→ 依赖"语音为主"的设计假设在这类视频上不成立。

### P5 动作语义无法从画面获得(能力边界,非 bug)

AI 提取只吃文本(语音 + 画面文字),**帧从不送进模型**。所以"搅碎/打发/抹平"这类
动作只能靠字幕文字描述;要让模型真看懂动作,需要多模态模型(VLM),当前 LLM 通道
(Command Code 端点的 deepseek 文本模型)不具备。

## 三、资源与代价(供方案取舍)

| 项 | 实测 |
|---|---|
| 单帧文件 | 480×852 jpg,约 97 KB(40 帧共 4.0 MB) |
| OCR | **1.17s/帧**(canvas 960;EasyOCR 默认参数为 5.5s/帧) |
| 图像向量(CLIP) | 约 0.3~1s/帧(CPU,批量 8 张更省) |
| 单条视频重跑 | 下载 + ASR + OCR 约 2~3 分钟(6.5 分钟视频、40 帧) |
| 现有旋钮 | `frames.max_frames=40`、`frames.frame_interval=5.0`、`frames.scene_threshold=0.45`、`vision.ocr.enabled=auto`、`vision.ocr.speech_ratio=0.3` |

## 四、约束(设计时别踩)

1. **表结构够用**:`chunks` 允许文本块带 `media_path`(即"步骤块 = 字幕文本 + 该帧图"
   不需要改表),`start_ts` 是 B站 `?t=` 跳转的依据,`seq` 只是展示排序用。
2. **判据已经存在**:`should_ocr` 已能识别"字幕/无配音视频"(人声占比 <30%),
   可以据此走**另一套抽帧策略**,而不影响正常有声视频。
3. 展示顺序按 `seq`;若要做"步骤流",需要展示层按 `start_ts` 混排(纯前端/API 改动)。
4. 成本随帧数线性:帧数 × (OCR 1.17s + CLIP ~0.5s)。180 帧 ≈ 额外 5 分钟/条。
5. 重跑同源视频会先删旧条目(带向量、FTS、队列任务),所以方案验证可以直接重跑 #14。
