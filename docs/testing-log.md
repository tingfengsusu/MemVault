## 2026-09-17 分析结果太简略的修复(用户反馈 #154)

### 问题现象

用户查看插件采集的视频条目(#154),只有一句路由理由"属于技术笔记范畴",
没有任何提取内容 → "太简略了"。

### 根因(两处)

1. **属性提取只在归档成功时执行**:留在待整理箱的条目既不归档也不提取,
   于是只有路由 reason 可见 → 已改为**无论路由结果都执行提取**
   (generic 提示词会自动归纳 3~6 个属性,内容具体到结论/数字/步骤);
2. **LLM 把分类提议写进 reason 却漏掉结构化字段**:路由返回
   new_category=null 但 reason="归入技术笔记(待确认)较合适" → 新增
   **reason 兜底解析**(正则识别"归入/归类为/建议新增/新建"模式);
   同时提议阈值放宽到 0.5(提议是待确认动作,不需高置信)。

### 修复后效果(#154 实测)

- 路由:proposed → **技术笔记(待确认)**(分类页可一键采纳)
- 提取内容:核心结论 / 推荐套餐与模型(含型号价格)/ 成本与用量(实测数字)/
  使用限制与技巧 / 中转站实测(5 家对比)/ 彩蛋与白嫖方法 —— 全部为具体信息

### 顺带改进

- 提取提示词升级:要求属性值"具体、包含实际信息,不要空泛概括"
- 路由提示词升级:无合适分类时必须给 new_category 提议

## 2026-09-17 属性键累积 bug(用户反馈 #154 有 10+ 行)

### 问题现象

条目 154 的 AI 属性出现 **15 个键**,含大量同义重复:
成本与用量/成本数据、彩蛋与白嫖方法/白嫖方法/彩蛋信息、关键要点/核心结论…

### 根因

`extract_item` 原来是"合并进 attrs_json"语义(为保护商品的价格/店铺预写字段)。
重复分析时,LLM 每次起的键名略有不同 → **同义键跨轮次累积,越分析越臃肿**。
(154 累计被分析了 3-4 次,15 键 = 3 轮提取的并集)

### 解决

新增 `items.attrs_ai` 独立字段:
- AI 提取写入 attrs_ai,**整体替换**(重新分析幂等,不再累积)
- attrs_json 保留给采集时预写的原始属性(商品价格/店铺等),互不干扰
- 迁移:启动时一次性把历史非商品条目的 attrs_json 移入 attrs_ai
- 详情页分两块展示:"AI 提取(重新分析会整体替换)"与"原始属性(采集时记录)"

### 验证

154 重新分析:15 键 → **6 键干净结果**;新增 2 个回归测试
(幂等无累积 / 商品原始属性不受影响);58/58 通过。

### 1. 双链相似度口径(用户质疑"#11×#13 相似度 0.64 真的这么高?")

**实测结论:不是真的相似,是口径问题。** links.py 原来是"条目正文前 600 字 → 去
**语义块**库里检索 → 取对方**任意单块**的最高相似度",阈值 0.55:

| 口径 | #11 × #13 |
|---|---|
| 旧(前 600 字 vs 最高单块) | 0.641 |
| 条目级整体比较 | 0.512(低于阈值,本不该连) |

更硬的证据:全库 66 对里旧口径中位 0.606、9 个候选对里 5 个超过 0.55;另一条已存
链接 **#4《心流》(心理学书) × #12 唱歌教程 = 0.645**,明显是误连。

**修法**:①比较文本改用 **AI 摘要画像**(`item_profile_text`:标题 + attrs_ai 值),
不再用充满口语填充词的原始 ASR 正文;②聚合方式改为**对方 top-3 块相似度的均值**
(单块撞词被摊平);③阈值按真实库分布重定为 **0.62**;④候选检索排除自己的块
(长视频自己的块会占满 top-k,导致 #11 一条相关条目都找不到)。

**连带修复**:`set_links` 原来删"触及该条目的所有行",后算的条目没找到对方时会把
先算的链接误删(真实:#8 算出与 #11 的 0.656 后又被抹掉)。改为只删自己这一侧的声明
(`item_a=item_id`),读取时两方向取高分去重。

**重建结果**:4 对 → **8 对**(心理学/关系类书互相连通;`#8 美国政府×英特尔 ×
#11 全球经济` 0.656 保留;`#12 唱歌 × #4 心流`、`#13 是,大臣 × #11` 等伪链接消失)。

### 2. 抽帧:全片覆盖(用户质疑"3 秒一帧 = 只看了 3 分钟")

用户说得对,而且原实现更糟:场景检测**扫到 max_frames 就停**(默认 16 帧),
44 分钟的视频只采开头几分钟。Video2Shop 原版也是这个逻辑(HSV 直方图相关性 < 0.45
判为切镜,取变化后的那一帧),MemVault 的移植版继承了它。

**修法** `vision/frames.py`:全片粗扫(上限 600 个采样点,记每个点的相邻相关性)
→ 时间轴分 `max_frames` 个桶 → **每桶取画面变化最大的点**(静态画面桶内无变化则取
桶首,保证均匀覆盖)→ 回头写盘。`max_frames` 默认 16 → **40**(config 可调)。

**真机验证**(#14,6 分 31 秒):`共抽取 40 帧(0.0s ~ 381s)` —— 铺满全片。

### 3. OCR 存档真正启用(用户同意"下载 ocr 吧")

- **依赖**:`easyocr 1.7.2` + `torchvision 0.29.0`(torch 2.14.0 未被改动,已核对
  pip freeze 差异);模型首次调用自动下载。
- **触发条件**(用户提议:不该不分情况跑两遍识别)新增 `config.vision.ocr.enabled`:
  `off` 不跑;`on` 一律跑(PPT/代码类);**`auto`(默认)**先看 ASR —— 人声时长占比
  < `speech_ratio`(0.3)才跑。管线顺序也改成"抽帧 → ASR → 按需 OCR"。
- **性能**:EasyOCR 默认参数 5.5s/帧,`canvas_size=960, mag_ratio=1.0` 后
  **1.17s/帧**(识别结果一致),40 帧约 1 分钟(首个视频含进程预热)。
- **真机验证**(#14):`画面 OCR 存档 40/40 帧有文字(人声仅占 7% < 30%,判为字幕/无配音视频)`,
  采到的是教学内容而非广告:「所有水果放入冰箱冷冻一夜」「就是清爽的蜜瓜冰淇淋」
  「芒果加百香果的搭配也是百吃不厌」「矿泉水瓶」「成功打发」。
- **关键补充**:画面文字必须并入 `content_text`,否则 AI 提取仍只看语音(第一轮验证
  时 AI 依然总结成"转转广告",因为正文只由 ASR 拼成)。并入后重新提取:#14 现在给出
  「关键食材与工具(蜜瓜/芒果/百香果/榴莲/奥利奥/朗姆酒…、矿泉水瓶、350ml)」「制作方法
  与步骤(冷冻一夜/组装/打发/400 次咖啡/冷冻 20 分钟/裹焦糖酱)」「创意成品示例」,
  路由也从「数码产品优惠」改为提议 **「美食教程」**。

## 2026-09-17 夜:提取提示词升级 + 广告开关 + 按钮反馈(用户实测反馈)

### ① 提取"太简略":提示词逻辑升级(prompts.py)

用户拿 #14(12 个冰淇淋做法)对比:"总结只是一个简单的关键步骤"。旧提示词要求
"3~6 个属性 + 具体信息",但没说按什么维度拆,于是模型给了一句共同点。

新版提示词(v2)加了三层引导:
1. **按内容形态定属性名**:教学/做法类 → 食材与用量 / 制作步骤 / 时间与温度 /
   关键技巧 / 常见失败原因;评测资讯类 → 核心结论 / 关键数据 / 论据与案例 / 局限;
   商品类 → 价格与规格 / 卖点 / 适用场景 / 与同类差异;
2. **并列对象必须逐个展开**(多道菜/多款商品/多个方法),每个对象单独写自己的
   配料与步骤 —— 正是"12 个做法"这类视频缺的那一层;
3. 数字/比例/时长/温度/型号/价格/顺序**保留原样**,不许概括成"若干/适量/多个步骤"。

**出厂提示词跟随升级**:`ensure_seed()` 里比对 active 版本与出厂文本,只有"仍是未被
改写的出厂版"才升级(用户/LLM 改写过的保留),旧版退役可回滚 —— 与"提示词可进化 +
可回滚"的设计一致。

  运行期在末尾追加上这条策略(保证开关对所有提示词版本都生效)。
- 设置页新增下拉「视频/页面里的广告信息」(忽略 / 说明),保存即生效;
  `/api/settings` 往返有测试覆盖(含非法值回落 ignore)。

### ③ 按钮点击没有反馈(用户实测)

原因有两个:提示条原来渲染在**页面顶部**,而"重新分析"按钮在长页面底部(条目 #14
有 82 个语义块)——点了以后提示出现在屏幕外;按钮自身也没有任何变化。

修法:
- **悬浮提示**:`web/src/lib/toast.js`(全局状态 + `showToast`)+ `components/ToastHost.vue`
  固定在右下角(`position: fixed`,不随滚动跑掉),9 个页面统一换掉页面内提示条;
- **按钮自身状态**:条目详情页的动作按钮执行中显示「⏳ 正在排队…」、完成后 2.5 秒内
  显示「✓ 已排入队列」再还原,点击处立刻可见;
- 文案也写清了后果:"已排入 AI 重新分析队列 —— 任务页可看进度,完成后属性会自动刷新"。

真机验证(Playwright + 系统 Chrome,逐帧抓 DOM):点击后 150ms 按钮已变为
「✓ 已排入队列」,右下角(902,727 / 视口 1280×820)出现悬浮提示,2.5 秒后按钮还原;
同时任务表 38 → 39,新增 pending 的 `auto_process` 任务 —— 反馈与真实入队一致。

### 第 0 步:视频画像探针 `memvault/vision/frames_probe.py`

**一次解码**拿三份证据(顺序 grab → 24 条横带的全分辨率签名 192×16 + 全幅 96×96 +
留 10 帧给文字证据)→ 判据全是纯函数。CLI 验证入口 `scripts/probe_video.py`。

真机 #14(391s,480×852):

| 项 | 实测 | 设计稿预期 | 判定 |
|---|---|---|---|
| 字幕带 | **0.458~0.542** | 50~54% | ✓ |
| 动作事件数 | **81** | 76(±10%) | ✓ |
| 事件中位时长 | 1.8s | 2.30s | 同量级 |
| 阈值 | floor(P20)=0.1477 / enter=0.4432 / exit=0.2216 | 相对静息水平 | ✓ |

**判据关键修正(设计稿没写、实测才发现)**:带内"变化强度"必须取 **P50(中位)**,
不能用 P75 —— 水印带的 P50=5.6%(与设计稿 4.43% 吻合)但 P75=40.4%(被背景运动主导),
用 P75 时所有含文字带都在 40% 上下,**×3 分离度判据直接失效**(探针返回"判不出来")。
换 P50 后水印带 5.6% / 字幕带 38.5%(设计稿 37.50%),分离度 6.8×(设计稿 8.5×)。

**另一处护栏**:`settle_from_series`(成品展示段)在"以动作为主"的视频上 P20 会贴着动作
水平,导致全片被判成静止 → 加"门槛不低于典型运动水平就不判"的规则,返回空(红线②:
允许判不出来)。

耗时(本机、冷却状态):像素扫描 15.3s;整条探针 113.7s(其中 EasyOCR 冷启动 + 10 帧
文字证据占大头;管线内 OCR reader 已预热会省一截)。设计稿估 ~14s,偏乐观。
